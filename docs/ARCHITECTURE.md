# Architecture and execution boundaries

## Components and data flow

The local FastAPI service owns the operator UI, local job records, media upload, and notebook orchestration. It sends video-processing work to the configured LinQ workspace. The pipeline there decodes/samples frames, runs configured model stages, tracks detections, evaluates temporal rule candidates, and may request a local Qwen review. A candidate can be emitted as soon as supporting detector evidence is available, before optional Qwen review or final rendering. Model evidence and operator review are recorded separately. An uncertain or missing model result is not promoted to a positive decision.

| Stage | Current configured implementation | Where it runs | Evidence boundary |
| --- | --- | --- | --- |
| Person boxes | RF-DETR program through LinQ's TPU service | Authenticated LinQ TPU service | A detected person box is a candidate localization, not identity or safety state. |
| Phone boxes | YOLO26m ONNX model via ONNX Runtime CPU | LinQ CPU | Per-person ROI crops are enabled in the current config; boxes are then associated with person detections by a configurable geometric filter. This is not a phone-use classifier. |
| Cigarette boxes | v2 CigDet-trained RF-DETR ONNX model via ONNX Runtime CPU | LinQ CPU | The current per-model setting disables person ROI; cigarette inference is full-frame. A box means a candidate cigarette object, not that someone is smoking. |
| Clip classification | ConvNeXt-Tiny image encoder and trained clip heads | LinQ CPU | A temporal classifier output is a candidate signal; its training/sampling assumptions limit interpretation. |
| Visual-language review | Qwen3.5-0.8B Q4 GGUF through a local `llama.cpp` server/loopback bridge | LinQ CPU | Review is based on supplied ordered frames and may return unknown; it is not an independent ground-truth label. Uncorroborated action text is gated as unknown. |
| UI and orchestration | FastAPI service, browser UI, Jupyter/HTTP/WebSocket client | Operator host | The UI does not run the models. It is unauthenticated and should stay on loopback or behind an authenticated gateway. |

The authenticated notebook/TPU path is a LinQ external service boundary. It is not a local TPU driver and requires authorized LinQ credentials. No inference is configured to use an external model API, and no neural-network inference runs on the operator's local host. The UI host handles browser work and orchestration only; model stages are configured for LinQ.

## Input and media integrity

Video uploads are stored under generated job directories, hashed, and uploaded to LinQ in bounded chunks with remote receipts. The image-set API accepts an ordered list of ordinary JPEG/PNG files, validates format, size, pixel count, and common dimensions, then encodes one still per second into MP4. Its receipt preserves the original source names and SHA-256 hashes alongside the generated video's hash and marks `input_kind=image_set` and `synthetic_time=true`. A LinQ run verified an ordered three-image set and its original hashes/indices. This is stop-frame simulation: it does not provide actual motion, capture intervals, or measured elapsed time, and motion-dependent rules are rejected for this input type.

The optional local demo catalog is generated by `scripts/install_demo_examples.py` from an allowlisted source manifest. It downloads full Pexels sources only after validating the URL/redirect boundary, verifies the complete source SHA-256, and creates trimmed local excerpts/posters. Generated media and catalog are ignored by Git. The demo helper does not create labels, predictions, or operator decisions.

## Zones, filtering, and multiple cameras

Saved zones are snapshotted with job/camera evidence and can trigger candidate events when the configured person footpoint enters the polygon. Zones provide spatial context for candidate generation; they do not validate a violation. The event journal supports filters for type, camera, zone, and relative start/end time. The verified two-camera job isolates frames and retains CV-only events by camera. This does not provide cross-camera identity, synchronization, or live multi-stream inference. See the [requirements matrix](REQUIREMENTS.md).

## Model integrity and provenance

`assets.json` describes the v2 model bundle, archive digest, and hashes for each installed model. `scripts/install_assets.py` verifies the bundle and extracted artifacts. The RF-DETR ONNX runtime verifies its ONNX artifact hash, while the source checkpoint hash is configured provenance metadata: the runtime does not verify an export or parity receipt. TPU loader checks include the compiled program/report contract and digest. Runtime receipts report configured stages and device/provider information; a local unit test or mocked service is not proof of a LinQ hardware request.

The files [`provenance/service-features.json`](../provenance/service-features.json) and [`provenance/linq-verification.json`](../provenance/linq-verification.json) record accepted feature cases and run-level evidence, tied to the inputs and model/configuration hashes recorded there. They confirm execution and selected behaviors, not accuracy. See [QA](../QA.md) for scope and caveats.

## Operational limits

This is a prototype, not a certified safety system. There is no verified production real-time latency/SLA, hundred-camera capacity, accuracy/recall benchmark, or cross-camera person re-identification. Selected object misses are documented; an object box alone does not prove a smoking or phone-use action. People must review the evidence and make operational decisions. The service should only process media for which the operator has the required rights and authority.
